# 胡了吗 · 让一桌人把麻将账算清的结算助手

> **从“AI 帮我算这一手牌”，到“帮四个人记清一整场局”。**
>
> “胡了吗”是一个在 Hackathon 中从零完成、持续迭代到 Demo 4.0 的麻将牌局结算原型：玩家创建或加入同一牌局，连续记录每局输赢、自动汇总总账并保存整场战绩；当牌型复杂、规则拿不准时，再进入 AI 辅助裁判流程获得可解释的参考结果。

## 01. 项目是怎么诞生的：一个“胡了以后怎么办”的真实场景

麻将局里最容易让气氛卡住的，往往不是谁胡了，而是**胡了以后该怎么算**。

面对复杂番种、地区规则和底分，玩家容易凭记忆心算；同桌对规则的理解不一致，结算会变成争论；即使一局算完，整晚输赢也常常只停留在口头或纸上，结束后无法回看。

我们最初的想法很直接：让用户拍一张胡牌牌面，由 AI 识别牌型，再按照规则自动算分。这个版本验证了一个最小闭环——**牌面 → 识别 → 算分 → 账单**。

但第一次 Demo 评审后，导师提出了关键问题：

> 用户真正需要的不是“偶尔帮我算一手牌”，而是“把四个人打一整场的账算清”。

这让项目发生了核心转向。我们没有继续把拍照功能做得更重，而是重新回到牌桌上的真实行为：**每一局都会发生的是记分；只有少数复杂或有争议的时刻，才需要拍照和 AI。**

最终，产品从单人 AI 算分工具，转向了四人共同使用的牌局记账、结算与复盘助手。

## 02. 我们解决的到底是什么问题

### 痛点一：规则复杂，靠心算容易错

不同地区的玩法、番种、底分、封顶和付款方式并不一致。用户在胡牌之后要同时判断牌型、确认规则、计算金额，既慢也容易出错。

**产品回应：**在开局时先统一规则、底分、封顶等结算口径；每局结算中提供赢家、付款方式、番种、倍数和直接输入金额等明确输入，让结果有据可查，而不是依赖口头记忆。

### 痛点二：一桌人共享一笔账，争论没有“共同视图”

麻将不是单人任务。四个人都关心谁赢、谁付、当前分数和最后怎么转账；如果只有一个人手机里的单局结果，结算仍然缺乏共同确认的依据。

**产品回应：**以“牌局房间”为组织单位，承载四名玩家、当前积分、单局流水、总账和整场历史。产品主线不再是“算一手牌”，而是让整场牌局都有可回看的共同账本。

### 痛点三：高频操作不能打断牌桌节奏

真实牌桌上，用户不愿在每局结束后跳转多个页面、重复进入房间或重新找功能。工具如果比手写还麻烦，就不会被持续使用。

**产品回应：**最终版本将操作收敛为一条连续路径：

`创建/加入牌局 → 记一局 → 连续记分 → 查看总账 → 终结整盘 → 回看历史`

确认一局后，用户会停留在“记一局”页面，直接记录下一局；只有整场结束时才主动终结并保存快照。这是 Demo 4.0 最重要的体验设计。

## 03. 项目里最难的不是“加 AI”，而是三次产品判断

### 难点一：AI 该站在入口，还是只在关键时刻介入？

最初的设计把拍照识别放在主入口，视觉上很像一个 AI 产品，但它不符合真实使用频率：每一局都要结算，不是每一局都需要识别牌面。

我们在 4 人次快速测评中收到了相互冲突的反馈：

| 测评对象 | 关键反馈 | 对产品决策的影响 |
| --- | --- | --- |
| 导师 A（麻将玩家） | 计分功能实用，希望名称更贴近计分 | 证明结算主线对真实玩家有价值 |
| 导师 B（不打麻将） | 计分繁琐，希望放大拍照 | 提醒我们 AI 展示更直观，但不代表高频需求 |
| 现场同学 C（麻将爱好者） | 觉得省事，建议增加新手引导 | 需要降低上手门槛 |
| 现场同学 D（麻将玩家） | 认可拍照识别，但希望一人操作全桌、流程更简单 | 推动一人记分、全桌共享账本的设计 |

**我的判断：**不简单地“放大拍照”，而是按用户是否真实打麻将、功能是否高频来判断反馈权重。最终让**记分成为主线，AI 识别成为争议升级入口**：高频功能承载日常使用，AI 用在最需要判断、最容易终结争议的时刻。

### 难点二：算分结果必须让用户看得懂，而不是让 AI “猜一个数”

如果产品只给出一个总金额，用户仍然会问：“为什么是这个分？”这不仅不能减少争论，反而会让 AI 成为新的争论对象。

**产品设计原则：AI 负责辅助识别与解释；结算页面负责把可确认的规则、番种、付款方式和金额展示出来。**

因此 Demo 的 AI 裁判页不会只给出结论，而是同时展示：

- 识别到的牌型和牌面示例；
- 置信度；
- 番数与判断依据；
- 将结果带入结算的入口。

在实际产品中，部分信息（例如自摸、点炮、座位风、地区玩法）不能从一张照片中可靠判断。因此最终交互保留了用户确认与补充输入，而不是假装“拍照后全自动完成”。这也是让 AI 输出可被信任的必要边界。

### 难点三：如何把“单局工具”改成“整盘心智”

Demo 2 证明了我们可以放进房间、积分、总账、历史、AI 裁判等很多功能，但移动端内测也暴露了问题：入口太多，用户无法一眼知道下一步该做什么。

Demo 4.0 的改法不是继续加功能，而是删掉干扰主线的跳转：

- 底部导航从多个并列功能收敛为“首页 / 记一局 / 我的”；
- “首页”只负责创建或加入牌局；
- “记一局”成为整场中持续停留的操作中心；
- 房间面板、AI 裁判、总账和历史被收纳到需要时才访问的位置；
- “终结整盘”成为明确终点，保存完整快照后再进入历史。

这次迭代解决的不是视觉问题，而是用户心智问题：用户不必理解所有功能，只需要知道**开局后持续记分，结束后看总账**。

## 04. 从 Demo 1 到 Demo 4.0：每一次迭代都在回答一个问题

| 版本 | 当时要验证的问题 | 结果与下一步 |
| --- | --- | --- |
| Demo 1 | AI 能否把牌面识别与单局算分串成一个可演示闭环？ | 跑通“拍牌面 → 识别 → 算分 → 账单”，但单人使用感过强 |
| Demo 2 | 如何让四个人都参与同一场牌局？ | 增加创建/加入房间、四人积分、逐局结算、总账与战绩；AI 降为辅助功能 |
| Demo 3 | 怎样减少手机操作对牌桌节奏的打断？ | 删除冗余入口，首页只保留开局，复杂功能后置 |
| **Demo 4.0** | 怎样让用户理解一场牌局从开始到结束的完整过程？ | 连续记一局、终结整盘、保存历史快照，形成最终可体验闭环 |

最终版本不是“功能最多”的版本，而是最清楚回答了这件事的版本：**这款产品在一整场麻将局中，分别在什么时候、帮谁、解决什么问题。**

## 05. Demo 4.0 最终交付了什么

[`demo-4.0/`](./demo-4.0/) 是本仓库唯一推荐体验入口，覆盖以下流程：

1. **开局与建房**：选择地区规则、底分、封顶、圈数、牌友圈及四名玩家，生成房间码与二维码样式。
2. **连续单局结算**：选择赢家、三家支付或点炮一家、番种与倍数；确认后四人积分和单局流水同步更新。
3. **AI 辅助裁判样例**：查看预置牌型、置信度和判断依据，并将样例结果带入结算。
4. **总账复盘**：按四家最终得分汇总应收应付，并生成本场高光信息。
5. **终盘存档**：保存规则、房间码、局数、四家得分、单局流水和 AI 争议记录；在“我的”和“历史战绩”中回看。

### 如何体验

这是一个静态前端 Demo，无需安装依赖。直接用浏览器打开 [`demo-4.0/index.html`](./demo-4.0/index.html)。

建议按以下路径体验完整闭环：

1. 点击“创建牌局”，填写基础规则并生成房间；
2. 进入“记一局”，完成至少一局结算；
3. 可进入“AI 裁判”查看样例并带入结算；
4. 点击“终结整盘”，在“我的”或“历史战绩”查看保存结果。

## 06. MVP 取舍：我主动没有做什么

黑客松的目标不是做一个完整麻将平台，而是证明一个真实场景是否能跑通。因此我把范围限定在“开局、记分、结算、复盘”的闭环内。

| 优先完成 | 主动延后 |
| --- | --- |
| 规则、底分、封顶等开局口径 | 完整登录注册体系 |
| 四人同局积分与连续记分 | 真实支付、红包或转账 |
| 单局流水、总账与整盘历史 | 多人实时同步与后端服务 |
| AI 裁判的可解释交互样例 | 真实图像模型推理与完整地区规则库 |
| 轻量复盘与战绩展示 | 复杂社交系统、完整复盘动画 |

取舍原则是：**少做功能，多做闭环；少讲平台，多讲一个真实、高频、能被现场体验的场景。**

## 07. 作为作品集，这个项目说明了什么

这个项目不试图证明“我做了一个已经可以规模化上线的麻将产品”。它更具体地展示了我在时间受限、信息不完整的真实产品环境中，如何：

- 从一个具体生活场景提炼可验证的问题，而不是先堆叠技术能力；
- 处理相互冲突的用户反馈，并按使用场景和用户角色做判断；
- 把 AI 从噱头式主入口，调整为真正能解决争议的辅助能力；
- 用信息架构和交互连续性降低高频使用成本；
- 为 MVP 划清能力边界，明确哪些是已交付原型、哪些仍需真实数据与服务支撑。

如果继续推进，我会优先验证“连续第二局发起率”等使用频率指标，再针对真实用户所在地区补齐规则库、真实牌面数据集与识别准确率基线，而不是先扩展更多功能。
